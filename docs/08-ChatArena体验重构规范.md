# Chat Arena 体验重构规范

> 状态：当前唯一有效的体验、前端和交互规范。
> 更新：2026-08-24
> 说明：本文件替代旧版《08-互动图鉴Demo计划.md》。旧文件保留作讨论记录，不作为实现依据。

## 0. 先把方向说清楚

Chat Arena 不是一个带宠物侧栏的评测后台，也不是一款有复杂数值的宠物游戏。它是一本文本比较与生命成长结合的像素互动故事书。

它是一段 1–5 分钟的互动体验：用户先决定今天愿意做几道判断，再逐题比较两条匿名回复；每次选择都会留下一个理由和一个短反馈，三次固定的成长节点让一只聊灵逐步显形，最后才揭晓它长成哪一种伙伴。

体验主线只有一条：

```text
选择今天的长度与出生基因
→ 读一题，比较两条回复
→ 选择 A / B / 都挺好 / 都不行
→ 选择至多两个理由（可跳过）
→ 看到聊灵的即时回应
→ 进入下一题
→ 在 1/3、2/3、3/3 节点完成一次成长对话
→ 完成本轮后进入全书校对
→ 确认装订后揭晓物种并写入星谱
```

这轮只解决三个问题：

1. 用户能不能在 3 秒内知道现在要做什么；
2. 每次选择有没有明确、轻量、可期待的反馈；
3. 宠物是否从第一题就存在，而不是最后结果页才出现。

不要在首屏同时展示结果统计、题库管理、成长轴、模型分析和完整进化树。它们都保留，但属于第二层入口。

### 0.1 这版交互的核心纠偏

上一版把“像翻书”做成了装饰性的网页外壳，用户仍然是在后台卡片里答题。本版明确改成：

- **书页就是答题界面**：一道题是一组左右对页，问题、A/B 回复和判断共同组成一页；
- **翻页就是继续动作**：选择、理由保存后才进入下一页，不用等待长动画；
- **目录就是回看入口**：已完成页面可以回到任意一页修改，未答页面不能跳过；
- **完成后先校对再揭晓**：第三次成长结束进入全书校对，确认装订后才公开参考、统计和最终物种；
- **聊灵是书中的陪伴角色**：出现在书脊、页角和成长章节，不再作为独立数据侧栏；
- **AWGE 只提供启动仪式与物件感**，Apple 式清晰度负责可用性，原创像素资产负责记忆点。

## 1. 已确认的产品规则

### 1.1 本轮题数

用户只能选择当前题库确实支持的册长。公开版固定 9 个脱敏样本，因此只展示 `3 / 6 / 9` 题；9 题是推荐项，但不能替用户自动开始。导入题库只有在库存达到对应数量时，才能出现更长选项。

| 本轮长度 | 第一阶段 | 第二阶段 | 第三阶段 | 适合的承诺 |
| --- | ---: | ---: | ---: | --- |
| 3 题 | 第 1 题后 | 第 2 题后 | 第 3 题后 | “快速认识它” |
| 6 题 | 第 2 题后 | 第 4 题后 | 第 6 题后 | “完成一小段养成” |
| 9 题 | 第 3 题后 | 第 6 题后 | 第 9 题后 | “完整体验（推荐）” |

统一公式：

```js
milestones = [goal / 3, goal * 2 / 3, goal]
```

题数在出生和本轮开始时确定，提交第一票后锁定。刷新继续原本的题序和进度；题库不足时不提供超出库存的选项，不静默减少题数。

### 1.2 成长阶段

成长只有四个公开状态，用户不看分数：

```text
出生 → 初醒 → 成形 → 定型揭晓
```

三次成长对话固定使用以下问题：

1. “如果我今天没接住你，你会怎么对我说？”
2. “一句话走偏时，你会先在意什么？”
3. “如果我们只剩最后一句，你想留给我什么？”

回答可跳过，最多 180 个中文字符。跳过不阻塞流程，也不弹出“回答得更好会长得更好”之类的暗示。

### 1.3 投票与成长的关系

- A、B、都挺好、都不行只决定用户偏好记录，不直接决定物种；
- 每票最多选择两个理由，理由对共感、探索、分辨三条隐藏成长轴产生固定贡献；
- 修改理由时重算原事件，不重复累计；
- 成长回答由服务端做安全压缩和结构化分析，前端只接收短回应、摘要和公开阶段；
- 票数、结果统计和成长物种严格分开，宠物不能反过来影响榜单。

## 2. 用户流程与页面状态

不要用“页面里塞很多卡片”的方式组织流程，先按状态组织，再决定组件。

```text
WELCOME
  └─ SETUP（出生基因 + 本轮题数）
       └─ BATTLE_READY（题目与两条匿名回复）
            └─ VOTE_SAVED（选择已盖章）
                 └─ REASON_SHEET（理由，可跳过）
                      ├─ NEXT_BATTLE
                      └─ GROWTH_INTERLUDE（第 1/3、2/3、3/3 节点）
                           ├─ BATTLE_READY
       └─ REVIEW（全书校对）
            └─ FINALIZE（确认装订）
                 └─ REVEAL（最终揭晓）
                      └─ STAR_ATLAS / RESULTS
```

### 2.1 WELCOME：只让用户开始

首屏不是产品介绍页，而是一个可开始的“今天一局”。内容顺序：

1. Chat Arena 品牌和一句话定位；
2. 选择出生基因：澄光、绒云、异星；
3. 选择今天做 3 / 6 / 9 题；
4. 主按钮：“打开今天的聊灵手册”。

出生基因只展示气质，不展示完整进化树或最终物种：

- 澄光：克制、透亮、会把一句话接稳；
- 绒云：柔软、治愈、会记住情绪的温度；
- 异星：陌生、灵动、会带来意料之外的角度。

两个选择组可以在同一屏完成，不做多步注册式向导。主按钮在没有选择时禁用，并用一句短提示说明缺什么。

### 2.2 BATTLE_READY：一屏只服务一次判断

桌面端是一个“判断场景”，不是三块独立面板，也不是一张必须看完的整页书：

```text
┌─────────────────────────────────────────────┐
│ 题号 / 本轮进度                 聊灵状态物件 │
│                                             │
│ 用户最新一句（主视觉）                      │
│                                             │
│ A 回复                     B 回复           │
│                                             │
│ 你更愿意继续跟谁聊？  A / 都挺好 / 都不行 / B │
└─────────────────────────────────────────────┘
```

- 顶部只保留题号、`已完成 / 目标` 和聊灵的阶段胶囊；
- 用户最新一句是当前视线焦点，放在两条回复之前；
- A、B 两条回复是同等重量的“匿名页”，但只保留局部纸张 / 页签暗示，不画厚重的左右书皮；
- 聊灵区是一个可呼吸的视觉舞台：像素形态、短回应和下一阶段提示放在一起，不放结果统计、成长轴或管理按钮；
- “对话前文”默认收起，展开不改变投票栏位置；
- 投票按钮贴近回复底部，四个选项一眼可扫到；
- 侧边可以有聊灵，但不能让它抢过题目或把题目推到屏幕下方。

移动端改为单列故事流：

- 顶部成长胶囊固定在内容上方；
- A、B 回复纵向排列，保持同一模板；
- 投票栏使用底部固定或 sticky 区域，但必须留出安全底部间距；
- 投票栏不能覆盖回复正文，键盘用户也能顺序到达；
- 不强制横向滑动，翻页感通过内容替换和轻量过渡完成。

### 2.3 VOTE_SAVED 与 REASON_SHEET：先判断，再解释

投票后的顺序固定为：

1. 选择按钮进入选中态，输入短暂锁定，拦截双击；
2. 在按钮位置盖一个小印章，显示“已记下”；
3. 理由面板紧贴投票区展开，最多选两个理由；
4. 理由可不选，按钮文案从“继续”变成“跳过理由，继续”；
5. 反馈文字控制在 36 字以内，不展示模型判断过程；
6. 当前题目保存完成后才进入下一页。

理由标签使用真实、可理解的语言，例如“更懂我”“更自然”“更有增量”“更准确”“更克制”，不展示“共感 +2”这类内部轴名称。

### 2.4 GROWTH_INTERLUDE：成长是一个短章节，不是打断式表单

达到里程碑后，不直接自动跳下一题，也不把反思做成普通确认弹窗。进入一个 1 屏的章节过场：

```text
章节标题：初醒 / 成形 / 定型
聊灵短回应：一句话
成长问题：一问
输入框：最多 180 字，可跳过
主操作：留下这句话
次操作：先跳过
```

提交或跳过后，显示一次 700ms 以内的形态变化，然后回到下一题。3 题模式的三个节点都很短，不能让用户在每题之间重复填写长内容。

### 2.5 REVIEW：先校对，再装订

完成最后一道题和第三次成长对话后，进入全书校对。校对页列出每一页的选择、理由和成长章节状态；装订前可回看并修改。没有完成全部页或成长章节时，装订按钮保持禁用。

装订使用幂等的 `POST /api/companion/finalize`。装订成功后锁定本轮票据和聊灵物种，之后只读。

### 2.6 REVEAL：揭晓是终点，不是成绩单

用户确认装订后，进入一次完整揭晓：

- 显示物种名；
- 显示一句人格描述；
- 显示三条安全压缩后的成长痕迹；
- 显示出生基因和本轮题数；
- 提供“收入星谱”和“看结果”两个下一步。

不显示隐藏分数、三轴比例、模型提示词、置信度或用户原文。

## 3. 翻页感怎么做，不能怎么做

“像翻书”是交互节奏，不等于把整个页面做成厚重的 3D 翻页组件。

### 采用

- 题号和页码在替换时同步变化；
- A/B 回复卡在 400–520ms 内做轻微横向位移和淡入；
- 当前选择在原位置留下一个印章；
- 下一题提前取数，翻页期间不出现白屏；
- 在成长节点使用一次更明显的章节过场；
- `prefers-reduced-motion` 下只做颜色、透明度和焦点移动。

### 不采用

- 不使用 WebGL、第三方翻页库或长时间的卷页动画；
- 不让用户必须拖拽、横滑或等待动画才能继续；
- 不在每次投票后弹出全屏庆祝；
- 不用 emoji 充当宠物正式资产；
- 不把 AWGE 的页面、素材或导航结构直接复制过来。

## 4. 聊灵如何从第一题开始存在

六只正式像素资产必须服务于过程，而不是只服务于最终弹窗。

| 出生基因 | 最终伙伴 | 过程视觉语言 |
| --- | --- | --- |
| 澄光 | 芽啵、砾尾 | 透光、叶片、矿物折射 |
| 绒云 | 苔角、暖灯 | 苔藓、琥珀、夜林薄雾 |
| 异星 | 卷星、夜墨 | 午夜蓝、紫外光、星孢与洞穴 |

四个公开阶段：

1. 出生：显示基因专属的种子 / 胚光容器；
2. 初醒：显示眼睛、触角、尾巴等家族特征，不能提前暴露最终物种；
3. 成形：显示两种候选伙伴之一的非完整剪影，保留悬念；
4. 定型：使用现有透明 PNG 正式揭晓，并写入星谱。

陪伴回应必须短、具体、与用户刚刚的动作有关，例如：

- “我记住你很在意这句话有没有接住人。”
- “这一票让我多看见了一点细节。”
- “我还没长好，但已经知道要慢一点。”

不能在过程中显示数值、排名、轴名称或“你把它养成了更优秀的形态”。七种最终形态没有高低：暖灯鹿、风游鸟、定星猫、花火狐、静潮鲸、跃迁鱼、圆月灵；出生基因只决定材质与视觉语言，隐藏成长倾向决定物种。

## 5. 视觉系统：借鉴方法，不复制网站

整体不是“像素游戏皮肤”，而是：

**编辑工具的清楚秩序 + 可玩物件的意外感 + 像素生命的温度。**

### 5.1 视觉令牌

- 背景：暖白纸张，使用极轻的纸纹，不做大面积炫光；
- 文字：近黑炭色，正文优先可读性；
- 主色：当前出生基因只占一个强调色；
- 容器：细线、局部阴影、圆角和留白，不使用全局厚重描边；
- 互动：印章、书签、页码、轨迹点等少量可玩物件；
- 宠物：透明 PNG 最近邻缩放，禁止平滑插值发糊；
- 动效：投票反馈、成长变化和揭晓三类，其余尽量静态。

### 5.2 参考网站与可复用机制

| 参考 | 观察到的机制 | Chat Arena 采用 | 明确不采用 |
| --- | --- | --- | --- |
| [AWGE](https://awge.com/home) | 首页有“Press Start”式进入感，页面和物件更像可探索的玩具 | 把书签、印章、成长胶囊做成有性格的物件；首屏先让用户开始 | 不复制原站资产、混乱导航、重型脚本或商品站结构 |
| [Florence](https://www.new.annapurna.com/en/games/florence) | 情绪段落用不同的短交互表达，而非同一个表单重复 | 三个成长节点各有一个动作：输入、等待、显形 | 不复制剧情、人物或具体小游戏 |
| [Storyteller](https://annapurnainteractive.com/games/storyteller) | 书页和版面就是玩法容器 | 让题目、回复和章节在同一套“页”里推进 | 不复制拼图规则和美术 |
| [Reigns](https://www.devolverdigital.com/games/reigns) | 一个判断、一个后果、下一张卡，节奏非常清楚 | 保持“一题一判断”，投票后马上反馈 | 不把左右滑动设为唯一操作，也不压缩成只有二元选择 |
| [Monument Valley](https://www.monumentvalleygame.com/) | 每个场景只有一个强焦点，动效解释空间关系 | 每题只突出“最新一句”和当前选择 | 不复制错觉、关卡或建筑资产 |
| [Finch](https://help.finchcare.com/hc/en-us/articles/37779979512845-Going-on-an-Adventure) | 陪伴角色通过小行动和回应形成关系 | 让聊灵对刚刚的判断做短回应 | 不照搬任务、奖励和商业化系统 |
| [Chao](https://sonic.sega.jp/SonicChannel/topics/information/20240123_008440/) | 互动累积会影响性格和形态 | 用理由和成长回答形成隐藏倾向 | 不复刻角色、世界观或进化条件 |
| [Eevee 分支进化](https://www.pokemon.com/us/strategy/pokemon-rpgs-101) | 同一出生点可以得到等价的多种结果 | 同一基因下有两个无高低分支 | 不复刻名称、角色和视觉资产 |

AWGE 的作用是提供“可玩的物件感”，不是让页面变得混乱。所有灵感都必须经过 Chat Arena 的三个约束：快、清楚、可继续。

## 6. 页面结构与组件边界

首屏导航只保留：

- Chat Arena 品牌；
- 对话（默认）；
- 结果；
- 怎么长大；
- 题库管理（仅管理员可见）。

实现时按体验职责拆分，不再把所有状态堆进单一页面：

```text
ui/setup.js             出生基因与题数选择
ui/game-flow.js         题序、进度、状态恢复与幂等
ui/vote-feedback.js     投票、理由、印章与下一题
ui/growth-interlude.js  三次成长章节与跳过
ui/companion-stage.js   宠物阶段、回应和素材映射
ui/reveal.js            揭晓与星谱入口
styles/tokens.css       色彩、字级、间距、动效令牌
styles/arena.css        判断场景与响应式布局
styles/interlude.css    成长章节与揭晓
```

保持 Vanilla ESM、Worker、本地 API、静态适配器和 GitHub Pages Demo；不引入 React、第三方数据库、第三方模型或翻页库。

## 7. 需要保留的工程边界

- 本地 API 和 GitHub Pages 使用同一套题目、投票、成长和揭晓契约；
- Pages 模式使用 fixture + `localStorage`，刷新后继续，不依赖 Worker；
- 任何模型超时、拒答或结构错误都回退到版本化的本地规则分析，投票不能被模型阻塞；
- 回答原文不进入日志、D1 或 R2；揭晓只显示安全压缩后的成长痕迹；
- `/chat-arena/` 子路径下 CSS、JS、图片和六只宠物都必须用相对路径；
- 结果统计、题库管理、版本隔离和回滚能力保留，但不占首屏主叙事；
- `3 / 6 / 9 / 12` 只影响本轮题目数量和三个节点位置，不偷偷改变投票统计口径。

## 8. 实施顺序

### 阶段 A：先做可评审的静态视觉稿

只做 WELCOME、BATTLE_READY、VOTE_SAVED 三个状态，使用真实 Demo Case 和现有宠物资产。先确认“看得懂、愿意点、点完想继续”，不先扩展后端。

### 阶段 B：接入题数和三节点

接入 3 / 6 / 9 / 12、题目稳定顺序、刷新恢复、题数锁定、三个成长章节和跳过逻辑。

### 阶段 C：把宠物接入全过程

实现出生、初醒、成形、揭晓四个公开状态；删除通用占位宠物在主流程中的长期存在；正式 PNG 只在成形提示和最终揭晓使用。

### 阶段 D：结果、星谱和管理降级为第二层

结果页改成书后索引，星谱展示主伙伴与回声分身；管理页保留编辑能力，但不改变体验首屏。

### 阶段 E：全状态 QA

必须检查：加载、空题库、网络失败、重复点击、理由跳过、成长待回答、题库切换、完成、刷新恢复、320 / 390 / 768 / 1024 / 1440 宽度、键盘、读屏、44px 触控目标、减少动效和控制台零错误。

## 9. Demo 验收标准

一个第一次打开的人，在不读说明的情况下应能完成：

```text
选基因 → 选 3 / 6 / 9 题 → 投一票 → 选或跳过理由
→ 看到聊灵回应 → 完成三个成长节点 → 看到最终物种
→ 打开结果或星谱
```

验收重点不是“页面上有多少组件”，而是：

1. 主按钮始终只有一个下一步；
2. 当前题目和两条回复不被成长装饰压过；
3. 每次投票后 1 秒内能看到有意义的反馈；
4. 3 / 6 / 9 / 12 的三个节点始终按比例落在正确题号；
5. 六只像素宠物在过程和揭晓中都真实出现；
6. 结果数据和成长叙事互不污染；
7. 任何失败都有可继续的回退，而不是卡死或白屏。

只有这份规范通过视觉评审后，才进入代码重构和 GitHub Pages 推送。
